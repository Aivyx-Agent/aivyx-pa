# Command Center as a Logbook — Design

**Date:** 2026-10-01
**Status:** Approved in brainstorming; awaiting implementation plan
**Repo:** aivyx-pa (`crates/aivyx-ipc`, `crates/aivyx-channel`, `crates/aivyx-web`)

## Why

The Studio's home screen today is a typical dashboard: a row of stat cards
(Missions / Active / Routines / Audit Events / Chain), an agent-vitals rail,
and four panels (Active Missions, Routines, Audit Trail, Learning). Every
number on it is true, and none of it answers what the operator actually
opens the app to find out: *does anything need me, and what did my
assistant do while I was away?*

The Wick & Compass brand promises "intelligence you can read like a
well-built gauge, not guess at through a glowing dashboard". The home screen
should keep that promise. It becomes a **logbook**: one readable column,
written by the assistant in its own first-person voice, drawn entirely from
the record. It is never generated by a model.

## What the operator sees

The page is a single column. From top to bottom:

1. **Instrument strip.** One ruled, flat line of mono readings that replaces
   the stat cards and the agent rail:
   - daemon status;
   - the model, with context use in %;
   - spend today against the budget (when one is set);
   - memory count;
   - chain state (sealed ◆ / broken).

   Each reading links to its screen (Settings, Costs, Memory, Audit). A
   reading that is off-normal turns warn or rust: daemon offline, context
   ≥ 80 %, spend ≥ 80 % of budget, or a broken chain.
2. **Greeting.**
   - A Fraunces headline: "Good morning." / "Good afternoon." / "Good
     evening." The config stores no operator name today, so the greeting
     doesn't address anyone. Adding an operator name is out of scope.
   - Below it, a mono line with the date and when you were last active:
     "Wednesday 1 October · last here 9 h ago".
3. **Needs you · N.** Actionable cards, in this order:
   - **Approvals:** pending chat or tool approvals, with Approve / Deny.
   - **Proposals:** pending persona proposals and skill refinements, with
     Review, which opens the screen that owns the proposal.
   - **Went wrong:**
     - a failed routine run;
     - a notification that failed to send;
     - the model provider unreachable;
     - a memory contradiction awaiting resolution.

     Each card has a link to the screen that owns it.
   - **Due reminders,** with Done / Snooze (1 h).

   When there is nothing: "Nothing needs you." in quiet Plex text.
4. **Since you were last here.** A curated log of up to 12 lines, oldest
   first:
   - Each line is a mono time followed by a first-person sentence ("I tidied
     14 memories and merged 2 duplicates.").
   - Lines for failures use the warn colour on the time.
   - If there are more than 12 entries, a final line reads "and N more →
     Audit".
   - When the log is empty: "All quiet since you were last here."
5. **Coming up.**
   - The next 3 enabled routines, each with a relative time ("tmrw 07:00")
     and its name.
   - Then any missions in progress, as "Working on ‹goal›".
   - When there is nothing: "Nothing scheduled." with a link to Routines.

The existing "Start here" welcome card still appears on first visits, above
the greeting. The Missions, Routines, Audit and Learning panels leave the
home screen, because each already has its own screen.

## Daemon side

### One new query

The new request is `QueryPayload::GetBriefing`, answered by
`QueryResponsePayload::Briefing { briefing }`. It goes in `aivyx-ipc/src/protocol.rs`,
is purely additive, and is documented in `docs/DAEMON_IPC.md`.

```text
Briefing {
  last_active_unix: Option<i64>,     // None → log covers last 24 h
  window_start_unix: i64,
  instruments: Instruments,          // daemon, model, ctx %, spend/budget, memory count, chain
  needs_you: Vec<NeedsYouItem>,      // { kind, id, sentence, action_hint, link }
  log: Vec<LogEntry>,                // { at_unix, sentence, severity, link }
  log_more: u32,                     // entries beyond the 12-line cap
  coming_up: Vec<UpcomingItem>,      // { at_unix: Option<i64>, sentence, link }
  source_errors: Vec<String>,        // sources that could not be read
}
```

### Two parts, in a new `aivyx-channel/src/briefing.rs`

- **Gatherer.** Async. It reads only data that already exists:
  - missions and mission gates (routine runs are wrapped in missions, so
    their outcome and summary come from here);
  - pending persona proposals and the pending skill-proposal count;
  - due reminders;
  - notification history (`outcome_kind` failures);
  - memory contradictions;
  - the learning digest (tidy and merge counts);
  - the cost ledger (today's spend);
  - the memory count;
  - chain status;
  - provider health;
  - the schedules' `next_fire_unix_ms`.

  Each source is read independently. A failing source adds its name to
  `source_errors` and is otherwise skipped.
- **Composer.** A pure `fn compose(facts: &Facts, now: i64) -> Briefing`. It
  writes every sentence from deterministic first-person templates, applies
  the ordering, the 12-line cap and `log_more`, and turns each
  `source_errors` entry into a Needs-you line: "I couldn't read reminders
  just now." No model is involved.

### Last activity

- **What counts.** The daemon records `last_active_unix` on things the
  operator *does*:
  - a chat message from any front end (`SubmitInput`);
  - resolving an approval;
  - deciding a proposal;
  - completing or snoozing a reminder.

  Viewing does not count. Reloading the Studio keeps showing the same log
  until the operator acts, so the log never empties on refresh.
- **Where it's stored.** The value is persisted in the encrypted store, so it
  survives restarts.
- **Before any activity.** When nothing has been recorded yet, the window is
  the last 24 hours.

### Honest limits

The audit chain stores a hash of each tool call's arguments, not the
arguments themselves. Sentences can therefore say "changed 3 files" but
never name them, and they don't pretend to. Every log line carries a `link`
to the screen holding the full record (Missions, Audit, Memory,
Notifications).

## Studio side

### Data flow

- The Command Center sends `GetBriefing` on mount and on the existing
  home-screen poll cadence.
- Card actions reuse the existing commands:
  - approvals use `ResolveApproval`;
  - persona and skill proposals use their existing decide calls;
  - reminders use two new, small `FrontendMessage` commands, because the
    daemon has no reminder mutations over IPC today:
    - `CompleteReminder { id }` calls `ReminderStore::cancel` and replies
      `DaemonMessage::ReminderCompleted { id, ok }`;
    - `SnoozeReminder { id, secs }` cancels the reminder and re-sets it with
      the same message and targets, due `now + secs`, and replies
      `DaemonMessage::ReminderSnoozed { id, ok, due_unix }`.

    Both count as operator activity.
- After each action the Studio re-fetches the briefing. A card disappears
  only when the daemon's next briefing no longer contains it; there is no
  optimistic removal.

### Components

The components live in a new `crates/aivyx-web/src/command_center.rs`, so
`main.rs` (11.6k lines) stops growing:

- `InstrumentStrip`
- `Greeting`
- `NeedsYou` (renders `NeedsYouItem` cards)
- `Logbook`
- `ComingUp`

The "Start here" card is reused unchanged. Once nothing else reads the
`Dashboard` fields that only served the old panels, those fields are
removed.

### Visual rules

Visual rules follow Stitch / Wick & Compass:

- navy base;
- flat surfaces with 1px ruled borders and no blur;
- brass (#c9a24b) for primary actions and the "Needs you" label;
- rust for broken or offline states;
- Fraunces for the greeting only;
- IBM Plex Sans for sentences;
- IBM Plex Mono label-tech style for times, the date line and instruments.

## Empty and failure states

- **Empty.** Each section uses its quiet line: "Nothing needs you.", "All
  quiet since you were last here.", "Nothing scheduled." None of them uses an
  illustration or a celebration.
- **Daemon unreachable.**
  - The daemon reading turns rust and says "offline".
  - The page keeps the last briefing, dimmed, with a mono "as of HH:MM".
  - The page never goes blank.
- **One source fails.** The briefing still renders. The failed source
  appears as a Needs-you line (see Composer).
- **An action fails.** The card stays and shows the error inline under its
  buttons.

## Testing

- **Composer unit tests** (Rust, pure): fixed `Facts` in, exact sentences
  out. They cover:
  - every Needs-you category;
  - every log entry kind;
  - each empty section;
  - the 12-line cap with `log_more`;
  - the 24-hour fallback when `last_active_unix` is `None`;
  - a source error;
  - greeting time-of-day boundaries.
- **Gatherer tests** against a temporary store seeded with a mission, a
  failed notification, a due reminder and a persona proposal.
- **Reminder command tests:** Complete removes the reminder; Snooze moves its
  due time and keeps its message and targets; an unknown id gives `ok: false`.
- **Last-activity tests:**
  - `SubmitInput` and an approval each update `last_active_unix`;
  - `GetBriefing` alone does not;
  - the value survives a store reopen.
- **Daemon end-to-end** (`crates/aivyx-channel/tests/`):
  - `GetBriefing` over real IPC;
  - resolve an approval surfaced in the briefing;
  - the next briefing no longer lists it.
- **Live check:**
  - Build the Studio bundle and drive it with the CDP script against a seeded
    daemon.
  - Screenshot the empty, busy and offline states and compare them visually.
  - Workspace clippy has zero warnings and `cargo test --workspace` passes.

## Out of scope

- Model-written summaries of the day (the log is template-only by design).
- Recording tool-call arguments in the audit chain.
- Changes to the Missions, Routines, Audit or Memory screens beyond
  receiving links.
- Terminal (TUI) equivalent of the briefing. `GetBriefing` makes one
  possible later.

## Refinements from planning (2026-10-01)

Planning checked the design against the code. These refinements take
precedence over anything earlier in this spec that disagrees.

- **Reminder commands are queries.** Small daemon mutations already travel
  as `QueryPayload` variants (`SetBudget`, `DeleteNotifyTarget`). So the new
  commands are `QueryPayload::CompleteReminder { id }` and
  `QueryPayload::SnoozeReminder { id, secs }`. Both are answered by
  `QueryResponsePayload::ReminderUpdated { id, ok, due_unix }`, not by new
  `FrontendMessage`s.
- **"Last here" uses visits.** If the anchor were simply the newest action,
  approving a card on the Command Center would empty its own log. Instead,
  actions less than 30 minutes apart belong to one *visit*:
  - The log window starts at the last action of the **previous** visit.
  - Once 30 minutes have passed since the newest action, that action becomes
    the anchor.
  - The window is capped at 7 days, and the header then says "In the last 7
    days".
- **Which front ends count.** Only operator actions arriving over the daemon
  socket count: the CLI chat, the TUI and the Studio. Telegram, Discord and
  Slack run inside the daemon and are not counted in this version.
- **Approvals in "Needs you"** come from three places:
  - the Studio's own pending chat approval, which it already holds, rendered
    with the existing `ApprovalCard`;
  - pending mission gates, answered with `ResolveGate`;
  - team-mission gates, answered with `ResolveTeamGate`.

  A chat approval belongs to the connection that started the turn, so the
  daemon cannot list approvals belonging to other connections.
- **Dropped from version 1:**
  - *Memory contradictions.* Detecting them needs a model pass, which is too
    costly for a polled page; they stay on the Memory screen.
  - *Model provider down.* The daemon tracks no provider health to read.
  - *Context %.* No live context usage exists. The strip shows the model and
    its context window, as the agent rail did.
- **Spend is a rolling 24 hours.** It is summed from `LlmCost` audit entries
  over the last 24 hours, the same window the day-budget gate enforces, and
  is labelled "24 h".
- **What the log says.** Log entries are:
  - routine runs: wrapped routines carry their outcome; unwrapped routines
    only say they ran;
  - notifications sent or failed;
  - one summary line of completed non-read-only tool calls, named with
    counts ("I made 5 changes: fs.write ×3, calendar.create ×2.");
  - one line of memories saved.

  Finished team missions carry no timestamp, so they stay on Mission Control.
- **Refresh.**
  - The briefing polls every 10 s while the Command Center is open, not on
    the 1.5 s live poll, because it walks the recent audit chain.
  - After an action, the Studio sends the action and then `GetBriefing` on
    the same connection, so the answer already reflects the action.
  - A failed action shows one notice line above the cards.
